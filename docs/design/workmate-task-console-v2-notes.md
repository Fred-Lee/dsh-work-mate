# WorkMate 任务面板 · 原型 v2（PC / H5 两套）

> 文件：`docs/design/workmate-task-console-pch5.html`（单文件，无外部依赖，双击即开）
> 截图：`docs/assets/ui/proto-v2-*.png`

## 为什么重做

现有面板有三个具体问题，不是审美偏好：

1. **四个等宽空盒**。没数据时 80% 屏幕是边框和"暂无任务"，读起来像设计稿，不像工具。
2. **「需要我」排在第三列**。这是唯一必须人动手的地方，却和「待办」「已完成」同等视觉权重，提问原文还藏在详情抽屉里。
3. **卡片是字段平铺**。标题、状态、仓库、时间同一字号同一灰度，没有主操作，也看不出"这件事走到第几步"。

## 改成了什么

| 原问题 | 处理 |
| --- | --- |
| 四个空盒 | 三列（待办 / 执行中 / 已完成）+ 顶部一条「需要你」带；空列用一行虚线说明收住 |
| 「需要我」不显眼 | 提成横贯的一条琥珀色带，**提问原文和回答输入框都在带上**，不用点开 |
| 卡片看不出进度 | 每个卡片 3 个进度点（已创建 / 已执行 / 待验收），主操作按钮按子状态变化 |
| 层级平 | 状态色只用色相区分（执行中蓝 / 待你琥珀 / 完成绿 / 停止红），底色一律中性 |
| 不知道点了会发生什么 | 每张卡只有一个主操作：「指派」「去回答」「去验收」「重试」「重新打开」 |

`活动` 是独立的左侧导航视图（不在任务页底部），见下一节。

- 点卡片 → 右侧抽屉（458px，与列表**并排**，不遮住上下文）：进度轨 → 需要你处理 → 执行（Super-agent）→ 输入（WorkMate）。
- 窄到 1024 时列宽变紧，卡片底部改为单行、时间允许省略，按钮永远与元信息同行。

## H5 布局（<900px，也覆盖 768 iPad 竖屏）

```
┌───────────────────────────────┐
│ 任务  ●在线        [筛选][主题][桌面] │
│ ┌────────┬────────┬────────┐  │
│ │需要我 2│进行中 5│已完成 4│  │   ← 分段切换，不横向挤压
│ └────────┴────────┴────────┘  │
├───────────────────────────────┤
│ 待回答  迁移脚本要不要… · 3 分钟前   │
│ 旧目录里还有 3 个未合并分支，删了就找  │
│ 不回来。要我跳过这 3 个…             │
│ ┌───────────────────────────┐ │
│ │ 回答 worker 的提问          │ │   ← 直接可点，不弹窗
│ └───────────────────────────┘ │
│ [ 看详情 ]  [   发送回答    ]   │
├───────────────────────────────┤
│ 执行中 ●●● dsh-Helmsman  P1 1 分钟前│
│ 把 wiki 导出的 front-matter 补上 tags│
│ [ 详情 ] [ 查看投递 ]            │
│                          (＋)  │   ← 拇指可达
├───────────────────────────────┤
│     任务   提案   团队   控制台     │   ← 底部 tab
└───────────────────────────────┘
```

- 详情改成**底部抽屉**（90vh，圆角 + 拖拽把手），新建改成全屏 sheet。
- 所有可点区域 ≥40px；输入框 16px 避免 iOS 聚焦自动放大；底部留 `env(safe-area-inset-bottom)`。

## 活动视图（历史记录 + 快捷搜索）

按「从历史记录里快速定位」的要求，活动从任务页底部挪成了 PC 左栏的独立入口，
H5 则作为分段里的第 4 项（底部 tab 的「控制台」也让位给「活动」）。

```
活动                                    [ 搜标题、仓库、Ticket、事件   / ]
任务与 Ticket 的过程记录 · 15 条 | 4 条匹配
(全部) (提问) (验收) (完成/停止)

今天 ─────────────────────────────────────────────────────────
14:02  ●  迁移脚本要不要连带删除旧 [worktree]？                  [提问]
          旧目录里还有 3 个未合并分支… · worker · 8045739609c6
13:12  ●  提案 adopt-superagent-openspec-source 已实现，等验收   [执行]
          [Ticket] 9bdb818370e3 开始执行（person/review）· super-agent
```

- **检索范围**：标题、仓库、事件原文、Ticket id、提案 id、操作者。命中词用 `<mark>` 标出。
- **快捷筛选**：全部 / 提问 / 验收 / 完成·停止（对应需要人决断与收尾三类）。
- **键盘**：`/` 直接跳到活动并聚焦搜索；回车打开第一条匹配；`Esc` 清空。
- **点击结果**：直接打开该任务的抽屉，不再需要先去列表里找。
- 移动端把搜索框和筛选条固定在内容区顶部（不是视口 sticky），避免和底部 tab 抢空间。

## 已定下来的三件事（2026-11-02）

1. **平板竖屏（768–899）继续走 H5 壳**。断点仍是 900；如果以后想给 iPad 三列，把断点调到 760 即可，其余不用改。
2. **活动独立成视图**，带搜索与筛选，见上一节。
3. **不做下拉刷新**。H5 只用 5 秒轮询，并且不劫持纵向手势（`touch-action` 不动），避免和手机远程壳的返回/切页手势冲突。给远程壳留了手动「刷新」入口的位置，但没有做下拉。

## 两个布局可调的事实

- PC 三列同时可见，**需要横向空间**；H5 用分段切换，同一时刻只显示一类，避免 320 宽度下四列被裁（这正是原面板的缺陷）。
- 「只看需要我」在两套布局里语义一致：PC 收起三列，H5 收起分段只留待办卡。

## 与实现的对齐

原型里每张卡的字段都来自现有的 `GET /api/tasks`（`TaskCardView`），没有新增接口：

| 原型元素 | 数据来源 |
| --- | --- |
| 标题 / 意图 / 仓库 / 优先级 / 时间 | `task.title` / `intent` / `repo` / `priority` / `updatedAt` |
| 状态徽标与进度点 | `substate`（`SUBSTATE_LABEL` 的子集） |
| 「需要你」带里的原文 | `note`（`person/*` 时是提问原文或验收摘要） |
| 详情里的 Ticket / 阶段 / 目录 | `ticket.id` / `stage` / `action` / `ended` / `directory` |
| 顶部在线状态 | `health.online` / `health.reason` / `health.paused` |
| 计数 | `lanes` 与 `attention` |

需要新增的只有一条聚合：`最近更新` —— 按 `updatedAt` 倒序取前 6 条，可由客户端算，也可以加一个 `GET /api/tasks/activity`。

## 原型里可以点的东西

| 操作 | 结果 |
| --- | --- |
| 点卡片 / 详情 | 开抽屉（PC 侧滑 / H5 上滑） |
| 「需要我」里输入回答并回车或点发送 | 该条移到「执行中」，模拟回答后的状态 |
| 「指派」 | 未指派 → 待接受（模拟写 `assigned` + `attempt=1`） |
| 「＋新建待办」 | 创建并指派 / 仅记录，两种落点都演示了 |
| 顶部「只看需要我」 | 收起其余列 |
| 左栏「演示：模拟离线」 | 切换掉线态（横幅 + 卡片 `unknown`） |
| 左栏「切换明/暗」 | 明暗切换（默认跟随系统） |
| 左栏「预览手机版」 | 强制渲染 H5 壳（窗口宽度不变也能看） |
| H5 右上角桌面图标 | 切回 PC 壳 |

## 实现时要新增的两条接口

活动视图需要一个只读的聚合端点，不要在前端拼：

```
GET /api/activity?q=&kind=&before=&limit=50
→ { items: [{ at, kind, label, taskId, title, repo, ticketId?, proposalId?, actor, text }], next? }
```

数据来源应当是 `workmate/events.jsonl`（已有 `task-create` / `task-assign` /
`team-dispatch` / `team-settled`）加 `tasks.json` 的当前投影；**不要**另存第三份活动表——
事件流已经是唯一事实源。

搜索先用服务端 `q` 过滤（子串匹配足够）；等条目多到需要排序质量时再接判断层的
`search-rerank`，不要一开始就上向量检索。
