## 背景(Context)

Helmsman 的插件运行在 DSH 宿主内部。与宿主的交互面没有集中文档，知识点分散在三处：
`docs/WORKBENCH-SETUP.md`（版本对齐）、`docs/SECURITY-AUDIT.md`（信任边界）、以及代码注释。
本次任务把"集成契约"单独收拢成一份文档，动机有两个：一是看板/工作项计划会大量触及宿主交互
（会话绑定、事件流、preset 插入），二是相邻项目 DSH-Work-Buddy（MIT，v0.1.998）已用生产代码
踩过其中几个坑，其经验可直接复用——但**必须与已验证事实区分开**，否则会把别人的结论当作本机
事实使用。

## 目标 / 非目标(Goals / Non-Goals)

**目标：**
- 一份可检索的集成参考，每条要点带证据等级与复现依据。
- 把本次实测得到的结论固化（Origin 围栏矩阵、bundle 声明要求、真机行为清单）。
- 记录"哪份 harness 可用于冒烟"的结论，避免下次再比一遍版本。
- 修掉 `@helmsman/artifacts` 的 bundle 声明缺失（已导致 profile 装载失败）。

**非目标：**
- 不把借鉴内容当规范：B 级条目只作设计输入，落地前须各自验证。
- 不改运行时行为；不引入 WorkBuddy 的代码（仅借鉴模式与结论）。
- 不做完整 DSH 宿主机能清单（只记录 Helmsman 触及的面）。

## 决策(Decisions)

### D1. 证据分级写入文档，而非单一"参考资料"清单
每条要点标 **A 实测 / B 借鉴 / C 源码**，A 级附可复现命令与结果。
- **理由**：借鉴结论的可靠性远低于本机实测；混排会让后续读者（或 agent）把未验证结论当作事实，
  这正是本次评估中要避免的风险。分级让"可以依赖什么"一目了然。
- **替代**：只写"参考"不分级（无法判断可信度）；或用一句话标注整篇（粒度太粗）。否决。

### D2. Origin 围栏以实测矩阵固化，而非转述他人结论
WorkBuddy 的注释称"DSH 只接受自身 host 的 Origin"，本次在本机 `0.1.2-alpha.5` 上用四种
Origin（不带 / 自身 / 外来端口 / 外来域）实测，得到 `401 / 401 / 403 / 403`，写入矩阵。
- **理由**：转述的结论可能带有对方版本的前提；实测把结论绑定到本机版本，并顺带发现
  "不带 Origin 的服务端调用不受围栏影响、只受令牌约束"，这是转述里没有的信息。

### D3. 文档落在 `docs/`，不落 spec 正文
可复现的操作性参考放 `docs/DSH-INTEGRATION-NOTES.md`；spec 只约束"必须分级、必须覆盖哪些
契约点、B 级不得冒充事实"这类可校验要求。
- **理由**：spec 一旦写具体命令就会与版本漂移脱钩；docs 允许追加而没有 spec 变更成本。

### D4. 缺陷修复：插件包声明齐备 + 文档记录该类的"测试盲区"
`@helmsman/artifacts` 缺 `dsh.bundle` 声明与 `cordis.patch.yml`，13 个同门包都有，唯它缺。
补齐三件（声明、补丁、README），并在文档里写明**单元测试抓不到这类缺陷，必须真装一次 profile**。
- **理由**：这是本次真机冒烟最有价值的产出——它暴露了"测试全绿但装不上"的盲区；
  把盲区写进文档比只修一次更有价值。

## 风险 / 取舍(Risks / Trade-offs)

- [B 级内容被误用为事实] → 分级 + 文首显式警告"不要把 B 级当已验证"。
- [文档随版本漂移] → 每条实测标出所用 harness 版本（`0.1.2-alpha.5`），版本变化时可定位失效条目。
- [WorkBuddy 上游变化导致引用失效] → 只引用具体文件与机制名，并标出其版本 v0.1.998。

## 迁移计划(Migration Plan)

纯新增文档 + 一处声明修复，无迁移。用户环境需在 `~/.dsh/profiles/web/package.json` 增加
`@helmsman/artifacts`（已在本机完成）。回滚 = 删除文档与 artifacts 的 bundle 声明。
