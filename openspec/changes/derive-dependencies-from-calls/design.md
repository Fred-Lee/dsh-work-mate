## 背景(Context)

`scan-rest.ts` 已能从一个服务的源码树抽取**对外暴露**的 HTTP 端点(Spring `@RestController` +
`@*Mapping`、NestJS `@Controller` + 装饰器、Express 风格 `router.get`),并有明确的有界策略
(深度/文件数/文件大小上限、`realpath` containment)。用户已用它扫出 341 个端点。

缺的是**对外发起**的调用。上一个变更(`simplify-service-dependencies`)把依赖"表达"降到一次录入
一条服务级边,本变更解决"发现":让工具把出站调用与已知端点对上,产出带证据的候选,人确认即可。

架构约束:memory-topology 是纯本地扫描器(零运行时依赖、无网络)。本变更必须延续这一点——
推导全部基于**本地文件**与**已存的拓扑数据**,不访问任何服务。

## 目标 / 非目标(Goals / Non-Goals)

**目标:**
- 把"谁调谁"从纯手工变成"工具提候选 + 人确认"。
- 每条候选带**可核验的证据**(文件/配置键/匹配端点),人不必相信系统的结论。
- 与已有去重语义组合后,确认候选不会造出重复行。
- 离线、有界、零新依赖。

**非目标:**
- 不做运行时探测(不调 `/actuator`、不抓流量、不连服务发现)。纯静态 + 本地。
- 不自动写入依赖(不自动合并候选)。
- 不做跨项目群的依赖分析;不做图形化拓扑渲染(仍是列表 + 候选清单)。
- 不追求 100% 召回:漏报可由手工补录(上一个变更已把手工录入降到两下拉)。

## 决策(Decisions)

### D1. 候选只提议、绝不自动落库
推导结果只经只读入口返回;落库必须由人确认(逐条或批量)。
- **理由**:名称/路径匹配本质是启发式,自动化必然引入错边;而错误的依赖会污染级联顺序与影响面分析,
  比缺边更有害。本仓已有同一取向的先例(看板"影响服务候选"需确认、合并冲突由人裁决)。
- **替代**:自动合并高置信度候选。否决——错边被静默写入后很难发现与清理。

### D2. 每条候选必须带证据,不产出无证据的猜测
证据 = 命中文件路径 + 配置键名 或 匹配到的端点。**无证据则不产出候选**(spec 中有对应场景)。
- **理由**:判定的责任在人,证据是让人能在几秒内判断的前提;没有证据的候选只会制造噪声并且不可反驳。
- **替代**:只给"置信度分数"。否决——分数不可核验,人无法据此判断。

### D3. 两档置信度,规则分开
- **名称档(高)**:目标服务的 id/name 出现在调用方基址/配置键/Feign 名中。**只做服务级边**(不带端点明细)。
- **路径档(中)**:调用方路径字面量与目标服务已声明端点匹配。先精确,再按段形状归一化
  (段数为占位符或字面量,忽略占位符名称差异),匹配成功时**带上该端点作为明细**。
- **理由**:名称线索几乎不会错(配置键就是为调用那个服务而写的),但给不出端点;路径线索能给出端点,
  但模板归一化会带来假阳性(如通用 `/api/health` 命中多个服务)。分开档位让人按档处理。
- **替代**:单一分数(信息量不足)。或只做名称档(拿不到端点明细,浪费已扫的 341 个端点)。

### D4. 成环候选单独标出,默认不勾选
若候选与**既有图**构成环,标记为「将形成环」并默认不勾选。
- **理由**:环是用户在 `simplify-service-dependencies` 中声明的架构不变量;推导出环有两种可能——
  真实的架构问题(应当知道),或匹配误报。二者都不该静默丢弃,也不该默认被写进去。
- **替代**:直接过滤(丢掉信息)。否决。

### D5. 结果去重与自环排除在推导层完成,落库复用既有合并语义
推导层按 (from,to) 合并多条线索(证据与端点取并集、置信度取高档),排除自环;确认落库时调用
`service-dependency-graph` 的按服务对合并(`mergeDependencyEdge` / 保存去重),因此任意一对服务仍只占一行。
- **理由**:两道去重职责不同——推导层去重是为了结果可读,落库层去重是为了不变量(`一对一条边`)
  对**所有**写入路径成立。两者都需要。

### D6. 扫描复用 scan-rest 的有界与 containment 策略
同样的深度/文件数/文件大小上限与根目录 containment,只读 `node:fs/promises`,不引入依赖。
- **理由**:同一份安全与资源纪律,避免出现"第二套扫描器有不同上限"的漂移。

## 风险 / 取舍(Risks / Trade-offs)

- [模板归一化假阳性] → 归于中置信度档 + 必须附匹配到的端点作为证据;人可逐条忽略。
- [单仓多服务导致自匹配混乱] → 以服务的 `localPath` 为扫描根;目标候选只在同群已声明服务中匹配,
  不猜未登记的服务。
- [大仓库扫描耗时] → 沿用既有上限;推导按需触发(用户点「推导候选」),不放在启动路径上。
- [端点明细随代码漂移] → 明细只是证据快照;重跑推导即可刷新,不影响"一对一条边"的图结构。

## 迁移计划(Migration Plan)

纯新增:新扫描器 + 推导 + 只读/确认入口 + UI 区块。不迁移数据,不改既有拓扑字段。回滚 = 移除 UI 区块与
两个新入口(候选未被自动写入,故回滚无数据后果)。

## 开放问题(Open Questions)

- 确认入口粒度:逐条 `applyCandidate` + 批量一次?倾向批量接口接受候选数组,内部逐条走合并语义。
- 是否缓存上次扫描结果(按服务 `localPath` + mtime)?倾向首版不缓存(按需重扫),避免失效判断复杂度。
- 路径归一化的占位符形态(`{}` / `{id}` / `:id`)统一到哪一种?倾向 `{}` 作内部规范形,展示时还原原文。
