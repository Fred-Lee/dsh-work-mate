# Design — Add Approval Records

## D1 门禁判据用 actor，不用"谁写的代码"

playbook 的原话是"写代码的 agent 无法批准"。在 DSH 里，工具调用与面板点击已经天然分成
两个 actor（M6 引入的 `EventActor`），所以最小的正确实现就是**按 actor 判**：目标状态在
`approvalsRequired` 里时，`agent` 被拒，`human`（REST/面板）与 `system`（插件内部编排）通过。
不引入"产出该 diff 的 actor"这种需要额外记录的溯源——actor 本身已经回答了这个问题。

## D2 拒绝要给出下一步，不是只说"不行"

错误文案写清三件事：哪个状态需要人工批准、去哪里批（面板「推进」按钮）、以及想全自动
该改哪个配置。历史上"卡住且不说怎么办"是这类门禁最容易被绕过（或被 `force` 粗暴跳过）的原因。

## D3 `force` 不跳过审批门

`force` 的语义（M4 起）是"只跳过审查门（缺 review.md / 未勾 CRITICAL）"，不碰其余前置。
审批门沿用同一纪律：它是另一类门，必须由 `allowAgentApproval` 或 `approvalsRequired`
显式改变，不能被 `force` 顺手绕过。这样"强制归档"不会静默变成"无需批准"。

## D4 审批也是事件

审批记录挂在提案上（投影/查询用），同一动作再写一条 `approval` 事件（审计用）。
两者是同一事实的两个视图：删掉事件流，聚合仍有审批；删掉聚合，事件流仍能重建审批链。
与 M6 的"事件是真相、度量是派生"不冲突——审批记录是**领域事实**，度量是派生。

## D5 记录 commit（能取到才记）

批准覆盖"哪一版"是审计的关键一格（对应社区调研里 worktable 的
"headSha + 一次性消费"教训）。取不到 git（未关联项目）时不阻塞批准，字段留空——
缺失是事实，不伪造。
