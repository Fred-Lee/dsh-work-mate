## 背景(Context)

用户诉求:把依赖索引前移到项目里,每个仓库提前声明对外依赖,Helmsman 抓取后由人**核对**即可,不必另行录入维护。

现有可复用管道(已核实):
- `import.ts` 的 `ImportPreview { source: 'docker-compose'|'kubernetes'|'openapi'; services[]; dependencies: [{from,to,method,endpoints}]; warnings[] }`
- 服务面 `importPreview(source, text, inferDeps?) → ImportPreview` 与 `importApply(group, preview)`;后者实现为
  "读现有拓扑 → `applyPreview` 合并 → `dedupeDependencies` → 存盘",即天然带成对去重。
- `ui-dashboard` 已有导入预览对话框(`ImportModal`),人工在其中勾选服务后应用。

两处缺口:
1. **边没有来源标记**。`RestDependencyEdge` 只有 `toServiceId`/`endpoints`/`method`/`critical`;无法区分
   仓库声明与推导确认。不补则"重新抓取"无法只调和声明边(会连同推导确认的边一起覆盖或残留)。
2. **没有仓库内声明文件的读取/写出**。

关键约束:`@helmsman/board` 的 WIP 与门控、以及 ③ 的推导与确认都不受影响——本变更只新增导入源、
一个可选字段与两个入口。

## 目标 / 非目标(Goals / Non-Goals)

**目标:**
- 仓库里一份小而显眼的 YAML 即可声明出站依赖;Helmsman 抓取后人工**只核对**。
- 重新抓取语义可预测:声明边跟文件走,推导边不受影响,重复抓取幂等。
- 声明文件可由工具**回写生成**,让"不用手写"成立。
- 文件缺失/损坏非致命且不静默。

**非目标:**
- 不做"声明 vs 代码"的漂移核对(下一变更:复用 ③ 的两侧数据)。
- 不声明入站依赖(反向由工具推导)。
- 不改 `importApply` 的既有合并/去重语义,只在其上加"来源调和"。
- 不做多文件聚合(一个仓库一份,仓库根固定位置)。

## 决策(Decisions)

### D1. 文件固定在 `<repo>/.helmsman/dependencies.yml`,只声明出站
- **理由**:`.helmsman/` 与本工具的家目录约定同名,位置显眼且不与项目现有目录打架;只声明出站让每条边
  只有一个家,从根上避免副本与视角矛盾。YAML 与既有拓扑导出同源,人手可读可改。
- **替代**:放进 `package.json` 字段(Java 项目不合适);放 `AGENTS.md` 散文(不可解析、会漂移、进每次
  会话上下文)——均否决。
- **格式含 `service`**:边的 `from` 必须可知,故 `service` 为必填;缺它直接拒绝解析(spec 有场景)。

### D2. 抓取 = 新导入源,复用"预览 → 核对 → 应用"
把文件解析成既有 `ImportPreview`(`source: 'helmsman-declaration'`),直接复用 `ImportModal` 的核对界面
与 `importApply` 的合并语义。
- **理由**:用户的"人工只核对"已经存在于该界面;新建一套审核 UI 是重复建设。也让声明文件与
  docker-compose/K8s/OpenAPI 三种导入共享同一条正确性路径(去重、悬空提示)。
- **替代**:独立抓取接口 + 自有确认界面(重复建设,且会与导入逻辑分叉)。

### D3. 边加 `source?: 'declared' | 'derived'`,缺省按 `declared`
`normalizeTopology` 保留该值;`mergeDependencyEdge` 在合并同对时,来源取"更保守"的一方(任一为
`declared` 则结果 `declared`)——避免推导确认把声明边降级。
- **理由**:调和规则必须能区分两者,否则"重新抓取"无法只动声明边;缺省按 `declared` 让存量数据
  (无该字段)自然纳入调和,而 ③ 的新增确认边显式写 `derived`。
- **替代**:不加字段而用 method 标记(`DEPENDS_ON` 之类)混用语义——脆弱且不可判定,否决。

### D4. 调和 = 声明边与文件求差集(增/删),`derived` 边不动
抓取应用时对同一 `service` 的边集合做:文件中有的补上、文件没有的 `declared` 边移除;
`derived` 边原样保留。因此重复抓取幂等。
- **理由**:仓库是声明边的唯一事实源,文件删了边就该消失;而推导确认的边没有仓库归宿,不能因一次
  抓取被"清理"。这也让两种来源各守其位:声明描述意图,推导补充发现。
- **替代**:全量覆盖(会吞掉推导结果);只增不删(文件失去权威,陈旧边永久残留)——均否决。

### D5. 未登记目标复用 ③ 的"登记并确认"路径
预览里标出未登记目标,允许在同一流程内登记服务。
- **理由**:真实数据里 6/7 个目标是未登记的;不提供登记路径,应用后立刻全是悬空引用(与 ③ 同一个坑,
  用同一个解法)。

### D6. 回写只输出 `declared` 边
`回写声明文件` 把某服务的 `declared` 边序列化为 YAML(与解析器互为往返),`derived` 边不写入。
- **理由**:回写的用途是"把当前声明固化到仓库/把已确认的推导提升为声明"。若把 `derived` 一并写入,
  等于把系统发现静默固化成"仓库声明",下次无法区分来源,且会让推导结果失去可追溯性。要提升为声明,
  应由人显式操作(确认后即刻回写)。

## 风险 / 取舍(Risks / Trade-offs)

- [文件与真实代码脱节(声明腐烂)] → 本变更不做校验,但**下一变更**做漂移核对;且回写让更新成本接近零。
- [有人手写错 `to` 指向不存在的服务] → 预览阶段按未登记目标标出并可登记;体检也会报悬空。
- [`derived` 边永不清理而积累] → 由 ③ 的确认流程与体检负责(成环/悬空会被报出);不在本变更扩大范围。
- [同一对既声明又推导] → 合并为一条,来源按 `declared`(声明优先),明细取并集;与既有成对去重一致。

## 迁移计划(Migration Plan)

纯增量:新文件、新导入源、可选字段。存量拓扑(无 `source`)按 `declared` 参与调和;不迁移数据。
落地顺序:类型/归一化 → 解析器与回写器 → 导入源接入 → 调和逻辑 → UI 入口 → 文档。回滚 = 移除入口与
导入源;数据不受损(`source` 为可选)。

## 开放问题(Open Questions)

- 抓取入口的位置:放在现有「导入」对话框里作为一个来源选项,还是单独一个「📥 从仓库抓取」按钮?
  倾向后者(语义不同:导入是外部描述文件,抓取是本仓库自身声明),但复用同一个预览组件。
- 回写文件后是否需要提示"建议提交到仓库"?倾向在 UI 上给一句提示,不做 git 操作。
