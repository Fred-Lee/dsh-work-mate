## Why

用户提出:扫描 `@FeignClient` 成本高,能否**从 YAML 等配置文件分析推测**,查不到依据再提示人工确认。

先纠正一个事实认知(这影响成本论证):出站扫描是**纯本地文件扫描**,没有任何 LLM 参与,**不消耗
token**;在用户真实仓库(两个 Java 服务、共三千余文件)上完整推导实测 **~0.3 秒**。因此本变更的
价值不在省 token,而在三个真实收益:

1. **配置就是事实源**:该仓库的每个 Feign 客户端都在 `application-*.yml` 的 `feign-client-config`
   下登记,只读配置即可推出全部 7 个目标,无需读取任何 Java 源文件(实测现有推导的名称档候选本就
   大量来自配置线索)。
2. **配置证据比代码启发式更稳**:代码扫描靠正则与模板归一化,历史上产出过假阳性;"配置里写了要调谁"
   几乎不会错。
3. **更快、更可预测**:只读配置文件(该仓库实测 21 个)而非遍历全部源码(281 个);结果来源单一明确。

**代价(必须如实)**:仅凭配置会丢失**端点明细**(来自 Java 接口上的 `@GetMapping`)与
"配置了但从未调用"的区分。对以服务级边为主的用法可接受;需要明细时仍可显式深度扫描。

设计结论:推导增加**范围(scope)**——`config`(默认,快)/ `full`(配置 + 代码扫描,按需);
查不到依据的目标照旧走"人工确认"既有路径(不凭空猜测)。

## What Changes

- 出站扫描与推导新增 `scope` 选项:`'config'`(默认)| `'full'`。
  - `config`:walk 只收集配置文件(`.yml/.yaml/.properties/.env/.conf`),**不读取** Java/TS 源文件;
    产出仅来自配置线索(名称档)。
  - `full`:现行为不变(配置 + 代码),用于需要端点明细或配置不全的场景。
- 推导结果携带 `scope` 与各类线索来源计数,使"这次候选来自配置还是代码"可辨识。
- UI:「推导候选」默认 config 快扫,提供「深度扫描(含代码)」开关;漂移核对同样默认 config
  (其"未在代码中找到证据"措辞相应调整为"未在扫描范围内找到证据")。
- 查不到依据:维持既有规则——**无证据不产出候选**、未声明/未登记目标走人工确认;本变更不新增自动行为。

## Capabilities

### New Capabilities
- `derivation-scope`:依赖推导的扫描范围语义——`config` 默认快扫(只读配置文件、仅名称档候选)与
  `full` 深扫(配置 + 代码、含端点明细)的边界、结果对 scope 的标注、以及"无证据仍走人工确认"的不变式。

## Impact

- `packages/memory-topology`:`scan-outbound.ts`(walk 按 scope 过滤文件类型)、`derive-dependencies.ts`
  (透传 scope、结果标注)、服务面入口透传;单测(config 与 full 的产物差异、config 不读源码文件)。
- `packages/ui-dashboard`:「推导候选」的快扫/深扫开关与结果标注展示;漂移核对入口同默认;单测。
- `docs/USAGE.md`/`docs/ARCHITECTURE.md`/`docs/VERIFICATION-GUIDE.md`:两种范围的含义、取舍与切换时机。
