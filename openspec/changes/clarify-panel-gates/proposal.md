# 提案：面板门禁文案与看板语义澄清

## Why

2026-11-09 真机实测（1440px，Playwright + DOM 双重确认）发现三处文案会误导操作者：

1. **README 把 G2 与 G5 的理由收集混为一谈**。`README.md:649` 写"面板会问一句批准理由
   并写入审批记录"，该句位于「人工批准门（`merging` 与 `archiving`）」段落内，但读者
   容易连带理解为 G2（`reviewing→ready` 的方案确认）也要理由。实测：面板
   `App.tsx:795` 的「确认方案」直接调用、**不弹窗、不收理由**；只有 `advance` 进入
   受门禁状态时才 prompt（`App.tsx:251`）。G2 不收理由是正确的（`approval-gate/spec.md:41`
   的 `rationale?` 本就是可选），错的是文档表述。
2. **状态标签「提案分支」在卡片上缺上下文**。`App.tsx:69` 把 `proposing` 标为
   「提案分支」，与右侧日期并列显示成"提案分支 10/13/2026"，看起来像分支名或
   时间戳，实际是状态标签 + 更新时间。真机截图可见（卡片
   `harden-openspec-archive-step`）。
3. **看板列名与状态标签不同源**，读者要自己建立映射：看板列「方案」= 状态
   「需求输入」+「提案分支」；列「待确认」= 状态「评审中」；列「执行中」= 状态
   「待实现」+「实现中」。映射本身正确（`App.tsx:83-88`），但没有一处文档解释它。

## What Changes

- `README.md`：把「面板会问一句批准理由」限定到 G5（`merging`/`archiving`），
  并明确写「G2 方案确认不收集理由——`planHash` 本身就是确认凭据」。
- `README.md`：增一张八态 ↔ 看板五列的对照表，让"方案/待确认/执行中/待合并/已归档"
  与八个状态名的关系可查。
- 面板：`proposing` 的标签在卡片上补足上下文（例如「提案分支已建」），避免被读成
  分支名或时间戳。

## Capabilities

### Modified Capabilities

- `workbench-panel`：「主视图为任务」「工作台信息架构与共享控件」补充看板列与状态
  标签的对照契约——面板 SHALL 让读者无需查源码即可建立二者映射。

## Impact

- `README.md`（两处）、`src/client/App.tsx`（一处标签文案 + 可能的列名 title）。
- 纯文案与展示，无行为变化、无数据迁移。
