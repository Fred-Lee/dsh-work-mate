## 背景(Context)

两侧数据都已存在:

- **声明侧**:`readDeclaration(localPath)`(`declaration.ts`,上一变更落地)给出该仓库声明的出站边,
  每条标 `source: 'declared'`。
- **代码侧**:`deriveDependencies(topology, opts?)`(`derive-dependencies.ts`)给出候选,含 `confidence`
  (`high` 名称档 / `medium` 路径档)、`evidence[]`、`targetDeclared`、`alreadyDeclared`、`wouldCreateCycle`。

本变更只做**比对与呈现**,不新增扫描能力、不改声明格式、不改依赖图。

关键事实(决定措辞与判定口径):
- 扫描是**静态且启发式**的。名称档几乎不会错(配置键/Feign 名就是为调用那个服务写的),但**漏识别**
  是真实的:动态拼接 URL、Nacos 下发的路径、非 Feign 的私有 RPC 都可能扫不到。
- 路径档有**假阳性**(模板归一化后通用路径可能命中多个服务),初始版本就因此产出过一条不存在的依赖。
  故漂移判定只认高置信档,中置信单列。

## 目标 / 非目标(Goals / Non-Goals)

**目标:**
- 让"声明腐烂"可见:声明与代码的差异被持续报出,而不是等人想起来才发现。
- 判定口径保守:只认高置信证据,中置信单列;把"未找到证据"如实表述为**需要人工确认**。
- 只读、非阻断,处置仍走既有确认流程。

**非目标:**
- 不做自动修复(不自动改声明、不自动加/删边)。
- 不做跨服务的整体漂移报表(按服务核对即可;聚合视图留待有需要时)。
- 不试图提高扫描召回率(动态 URL 识别是另一条线,本变更只如实声明局限)。

## 决策(Decisions)

### D1. 比对面 = 声明边 vs **高置信**候选,中置信单列
`consistent` / `staleDeclared` / `undeclared` 三组的判定只用名称档候选;路径档候选单列
「可能未声明(中置信)」。
- **理由**:路径档的假阳性会让 `undeclared` 长出无数"看起来像新依赖"的条目,而这份清单的价值在于
  **可信**,一旦掺入噪声就会被忽略。名称档的证据几乎不会错,适合当判定准绳。
- **替代**:两档都算(噪声毁掉清单可用性);只报高置信且隐藏中置信(丢信息)。选"判定用高档、中档可见"。

### D2. `staleDeclared` 的措辞是"未在代码中找到证据",不是"不存在"
每条附"扫描为静态启发式,动态构造的调用可能未被识别"的说明,并引导人工确认后再删声明。
- **理由**:把漏识别误报成"该依赖已失效"会让人删掉真实依赖,进而让 agent 基于错的图推理——
  比不报更糟。这与本仓既有的"诚实降级"取向一致(不可判定就说不可判定)。
- **替代**:直接写"已失效,建议删除"。否决。

### D3. 只读 + 非阻断,处置走既有确认流程
核对只返回结果;`undeclared` 条目的"处理"跳进既有候选确认流程(可登记未登记目标、可确认依赖),
`staleDeclared` 的处置就是**人去改声明文件**(工具不代改)。
- **理由**:自动改声明等于把工具判断写进"意图"层,而意图应属于人;自动落依赖边同理。
  既有确认流程已经具备登记/去重/悬空提示,复用即可,不新建。

### D4. 无声明文件时是引导而非错误
结果明确说明"该服务未声明依赖,以下 N 条为代码证据,均未声明",并引导写回一份声明作为基线。
- **理由**:这正是用户当前的状态(两个仓库都还没有声明文件),这条路必须是**有用的起点**
  而不是一个错误提示。同时它也自然回答了"从哪开始"——先写回一份基线,再持续核对。

### D5. 呈现与图级体检并列,不合并
漂移告警条与既有 `checkHealth`(环/悬空/孤立)并列显示,各自独立。
- **理由**:两者性质不同——体检看的是图**自洽**(与代码无关),漂移看的是图**与代码一致**。
  合并会让"哪类问题"变得含糊。

## 风险 / 取舍(Risks / Trade-offs)

- [漏识别被当成陈旧] → D2 的保留措辞 + 引导人工确认;不提供"一键删除陈旧声明"。
- [漂移清单长期无人处理] → 只读告警,不阻断;价值在可见性,不在强制。
- [大规模服务的性能] → 每服务一次扫描(沿用既有资源上限);按需触发,不放在启动路径。
- [中置信分列被忽略] → 可接受:它本就是"供参考",判定不依赖它。

## 迁移计划(Migration Plan)

纯新增:一个比对模块 + 只读入口 + 一处界面呈现 + 文档。不改数据、不改声明格式。回滚 = 移除入口与
呈现(核对无副作用,故无数据后果)。

## 开放问题(Open Questions)

- 是否需要在漂移结果里包含"声明了但目标未登记"(悬空)?倾向不重复:图级体检已报 dangling,
  漂移区只链接过去,避免同一问题两处显示不同措辞。
- 漂移结果是否要能被导出(便于贴进 PR/issue)?倾向先不做,有需要时用既有 YAML/导出通道复用。
