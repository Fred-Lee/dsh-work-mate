# 设计：面板门禁文案与看板语义澄清

## D1 G2 不收理由，且不该收

`planHash` 是方案工件（proposal/design/tasks/specs）的规范化摘要，确认它等于
"我认可这一版内容"。再要一段自由文本理由没有增量信息，只会让批准记录里多一列空话。
规格 `approval-gate/spec.md:41` 把 `rationale` 定义为可选也支持这一点。

G5（`merging`/`archiving`）不同：那是**合并与归档的放行**，理由有审计价值
（"为什么这批代码可以进主干"），所以面板 prompt 是对的（`App.tsx:251`）。

结论：只改文档，不改行为。

## D2 看板列与状态标签必须可对照

现状映射（`App.tsx:83-88`，正确）：

| 看板列 | 覆盖状态 |
| --- | --- |
| 方案 | `draft`（需求输入）、`proposing`（提案分支） |
| 待确认 | `reviewing`（评审中） |
| 执行中 | `ready`（待实现）、`implementing`（实现中） |
| 待合并 | `merging`（合并校验）、`archiving`（归档中） |
| 已归档 | `archived`（已归档） |

不改映射（它是对的、也符合"人真正要动作的五件事"的意图），而是把这层映射写进
README，并在看板列头补 `title` 提示。

## D3 「提案分支」标签的歧义

`proposing` 的真实含义是"方案写在提案分支上、等评审"，标签「提案分支」单独出现时
容易被读成名字。改为「提案分支已建」并在列头/提示里说明，成本最低且不改变状态机。
